Прежде чем добавлять реплики или шарды, выжмите максимум из имеющейся базы. Обычно самый большой выигрыш при минимуме архитектуры дают два рычага. **Денормализация** хранит данные в той форме, которая нужна чтению. **Оптимизация** заставляет каждый запрос делать меньше работы. Оба рычага измеримы, обратимы и дёшевы по сравнению с распределением данных. И в обоих легко ошибиться, если следовать советам по памяти, а не по плану запроса.

<Aside type="tip" title="Коротко">
- Сначала измерьте: найдите запросы, которые съедают больше всего суммарного времени (`pg_stat_statements`, журнал медленных запросов), затем прочитайте их планы через `EXPLAIN ANALYZE`.
- Правильный **составной индекс** часто превращает полное сканирование таблицы в чтение нескольких страниц. Но каждый индекс замедляет запись и занимает память, поэтому добавляйте индексы только под реальные запросы.
- Избавьтесь от **запросов N+1**, используйте **пагинацию по ключу** вместо `OFFSET` и поставьте перед PostgreSQL **пул соединений**.
- **Денормализуйте**, когда чтений намного больше, чем записей, а узкое место — соединения. Решите, кто поддерживает копии в согласованном виде: транзакция, триггер, материализованное представление или поток событий.
- Многие классические советы устарели: `CHAR` в PostgreSQL не быстрее `VARCHAR`, `VARCHAR(255)` — привычка, а не оптимизация, а кэша запросов в MySQL больше нет.
</Aside>

## Денормализация

Нормализованная схема хранит каждый факт один раз, и запись остаётся простой и корректной. Чтение же собирает факты обратно через соединения. Денормализация хранит некоторые факты **больше одного раза** или хранит **заранее вычисленные результаты**, чтобы горячие чтения обходились без соединений и агрегатов.

Почему это окупается: многие пользовательские системы читают гораздо больше, чем пишут. На ленты, страницы товаров и дашборды нередко приходится 100 и более чтений на одну запись. Допустим, соединение стоит 2 мс на чтение, а поддержка копии — 1 мс на запись. При 10 000 чтений и 100 записях в секунду отказ от соединения экономит 20 секунд времени базы каждую секунду, а дополнительная работа при записи стоит 0,1 секунды. Для таблиц с интенсивной записью арифметика переворачивается.

Распространённые формы:

- **Дублирование столбцов.** Хранить `author_name` в каждом `post`, чтобы лента не соединялась с `users`.
- **Счётчики и агрегаты.** Держать `comment_count` в `posts`, а не выполнять `COUNT(*)` по комментариям при каждом просмотре страницы.
- **Заранее вычисленные представления данных.** Сводные таблицы, документы для поиска, ленты отдельных пользователей.
- **Встроенные дочерние записи.** Хранить позиции заказа внутри заказа в виде JSON, если их всегда читают вместе.

### Как поддерживать копии согласованными

У каждой копии должен быть владелец и путь обновления. Примерно по убыванию строгости:

| Механизм | Согласованность | Цена и риски |
|---|---|---|
| Одна транзакция обновляет обе копии | Немедленная и атомарная | Каждый писатель должен об этом помнить; горячие счётчики вызывают конкуренцию за блокировки |
| Триггер в базе | Немедленная, забыть невозможно | Скрытая логика; замедляет каждую запись; сложнее отлаживать |
| Материализованное представление с обновлением по расписанию | Устаревает между обновлениями | Полное обновление пересчитывает всё |
| Захват изменений (CDC) или события, обновляющие модель чтения | В конечном счёте, обычно секунды | Больше движущихся частей; потребители должны быть идемпотентными |
| Периодическая сверка | Исправляет расхождения | Обнаруживает ошибки, а не предотвращает их |

Транзакционный вариант для счётчика комментариев выглядит так:

```sql
BEGIN;
INSERT INTO comments (post_id, body) VALUES (42, 'Nice post');
UPDATE posts SET comment_count = comment_count + 1 WHERE id = 42;
COMMIT;
```

Какой бы механизм вы ни выбрали, добавьте запрос сверки, который находит расхождения, и запускайте его периодически:

```sql
SELECT p.id, p.comment_count, count(c.id) AS actual
FROM posts p LEFT JOIN comments c ON c.post_id = p.id
GROUP BY p.id
HAVING p.comment_count <> count(c.id);
```

### Материализованные представления

Материализованное представление хранит результат запроса как таблицу. PostgreSQL пересчитывает его по команде `REFRESH MATERIALIZED VIEW`. С `CONCURRENTLY` читатели во время обновления не блокируются. Для этого на представлении нужен уникальный индекс:

```sql
CREATE MATERIALIZED VIEW daily_revenue AS
SELECT date_trunc('day', created_at) AS day,
       sum(total_cents)              AS revenue_cents,
       count(*)                      AS orders
FROM orders
WHERE status <> 'cancelled'
GROUP BY 1;

CREATE UNIQUE INDEX ON daily_revenue (day);
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_revenue;   -- например, каждые 5 минут из планировщика
```

Встроенное обновление в PostgreSQL всегда пересчитывает запрос целиком; расширение `pg_ivm` умеет обновлять несложные представления инкрементально. В Oracle и SQL Server (индексированные представления) инкрементальное обслуживание части представлений встроено. На большем масштабе та же идея превращается в потоковый обработчик или CDC-конвейер, поддерживающий модели чтения. См. [потоковую передачу событий](/async/event-streaming/).

**Цена денормализации:** больше места, более медленная и сложная запись и постоянный риск расхождения копий. Под тяжёлой нагрузкой на запись денормализованная схема в целом может работать медленнее нормализованной. Денормализуйте конкретные горячие пути, а не всю схему.

## Оптимизация SQL

### 1. Сначала измерить

- **Профилируйте продакшен.** В PostgreSQL `pg_stat_statements` ранжирует нормализованные запросы по суммарному времени, числу вызовов и строк. В MySQL используйте журнал медленных запросов (с `long_query_time`) или дайджесты операторов в `performance_schema`. Оптимизируйте верх списка по **суммарному** времени: запрос на 2 мс, вызываемый 50 000 раз в минуту, важнее 3-секундного отчёта раз в день.
- **Проверяйте изменения нагрузочными тестами** с реалистичным параллелизмом и объёмом данных. `pgbench` и `sysbench` нагружают базу напрямую, k6 или Locust — всё приложение. Запрос, быстрый на 1000 строк, может стать катастрофой на 100 млн.

### 2. Прочитать план

`EXPLAIN` показывает план, выбранный оптимизатором. `EXPLAIN ANALYZE` выполняет запрос и добавляет реальные числа строк и время. В MySQL `EXPLAIN ANALYZE` есть с версии 8.0.18. В PostgreSQL добавьте `BUFFERS`, чтобы видеть затронутые страницы (с версии 18 счётчики буферов выводятся автоматически). Поскольку `ANALYZE` выполняет оператор, оборачивайте записи в `BEGIN; ... ROLLBACK;`.

На что смотреть:

- **Последовательное сканирование больших таблиц** там, где ожидался индекс.
- **Оценка и факт по строкам** расходятся в 10 раз и больше. Оптимизатор работает по плохой статистике: запустите `ANALYZE` или увеличьте ориентир статистики (statistics target) для столбцов с перекосом.
- **Сортировки и хеши, сбрасываемые на диск**, и вложенные циклы с очень большой внешней стороной.

Вот реальный пример на таблице `orders` из 2 млн строк (PostgreSQL 16, столбцы стоимости убраны для краткости). Запрос выбирает 20 последних заказов одного клиента (у этого клиента их всего 16):

```text
-- До: подходящего индекса нет
Limit (actual time=137.024..142.922 rows=16 loops=1)
  Buffers: shared hit=12691 read=4665
  ->  Gather Merge ... ->  Sort  (Sort Key: created_at DESC)
        ->  Parallel Seq Scan on orders (actual time=19.623..127.950 rows=5 loops=3)
              Filter: (customer_id = 42)
              Rows Removed by Filter: 666661
Execution Time: 143.080 ms
```

```sql
CREATE INDEX orders_customer_created
    ON orders (customer_id, created_at DESC) INCLUDE (total_cents);
```

```text
-- После: составной покрывающий индекс
Limit (actual time=0.047..0.051 rows=16 loops=1)
  Buffers: shared hit=4 read=3
  ->  Index Only Scan using orders_customer_created on orders
        Index Cond: (customer_id = 42)
        Heap Fetches: 0
Execution Time: 0.072 ms
```

План перешёл от чтения примерно 17 000 страниц (около 140 МБ) к 7 страницам и от 143 мс к менее чем 0,1 мс. Это примерно в 2000 раз быстрее — ценой индекса на 77 МБ, который теперь должна обновлять каждая вставка.

### 3. Индексировать осознанно

- **Порядок столбцов в составном индексе важен.** Индекс по `(customer_id, created_at)` обслуживает `WHERE customer_id = ?` и `WHERE customer_id = ? ORDER BY created_at`. Сначала идут столбцы с равенством, затем столбец диапазона или сортировки. Движки иногда умеют использовать индекс без его первого столбца (skip scan в MySQL, B-tree skip scan в PostgreSQL 18), но эффективно — только когда у этого столбца мало различных значений. Не проектируйте в расчёте на это.
- **Покрывающие индексы** содержат все нужные запросу столбцы, так что к таблице обращаться не приходится (`INCLUDE` в PostgreSQL; в InnoDB вторичные индексы всегда содержат первичный ключ). В PostgreSQL это работает только для страниц, которые карта видимости помечает как полностью видимые, поэтому перед прогоном примера таблицу обработали `VACUUM` (`Heap Fetches: 0`).
- **Селективность.** Индекс окупается, когда сильно сужает выборку. В нашей таблице у `status` четыре одинаково частых значения. С индексом по нему условие `status = 'paid'` всё равно возвращает 500 000 строк, разбросанных по всем 17 242 страницам таблицы, и запрос занимает около 200 мс что с индексом, что без. Никакой индекс не сделает дешёвым фильтр, под который попадает четверть таблицы. **Частичный индекс** (`... WHERE status = 'new'`) помогает, когда вы запрашиваете одно редкое значение.
- **Цена записи.** Каждый индекс добавляет работу каждому `INSERT`, каждому `UPDATE` индексированных столбцов и каждому `DELETE`. Он также конкурирует за память. Находите неиспользуемые индексы (`pg_stat_user_indexes.idx_scan = 0`, `sys.schema_unused_indexes` в MySQL) и удаляйте их.
- **Массовая загрузка.** При большой загрузке в новую таблицу сначала загрузите данные, а индексы постройте потом. Так рекомендует документация PostgreSQL, а `COPY` выигрывает у построчных `INSERT`.

### 4. Избегать запросов N+1

Цикл в ORM, который выбирает 50 постов, а затем автора каждого поста, выполняет 51 запрос. При RTT 0,5 мс это около 25 мс чистой задержки. Два запроса стоят около 1 мс:

```sql
SELECT id, author_id, title FROM posts ORDER BY created_at DESC LIMIT 50;
SELECT id, name FROM users WHERE id = ANY($1);   -- $1 = массив из 50 id авторов
```

Используйте жадную загрузку в ORM (`select_related`/`prefetch_related`, `includes`, `JOIN FETCH`), одно соединение или пакетирующий слой вроде GraphQL DataLoader. Следите за числом запросов на один HTTP-запрос в APM или логах.

### 5. Пагинация по ключу, а не OFFSET

`OFFSET 1000000 LIMIT 20` заставляет базу прочитать и выбросить миллион строк. К тому же страницы сдвигаются, если между запросами вставились строки. **Пагинация по ключу** (keyset, seek) запоминает, где закончилась предыдущая страница:

```sql
-- первая страница
SELECT id, created_at, total_cents FROM orders
ORDER BY created_at DESC, id DESC LIMIT 20;

-- следующая страница: передаём обратно (created_at, id) последней строки
SELECT id, created_at, total_cents FROM orders
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC LIMIT 20;
```

С индексом по `(created_at DESC, id DESC)` наша тестовая таблица отдала страницу 50 001 через `OFFSET` за 226 мс, а ту же страницу по ключу — за 0,18 мс. По ключу нельзя прыгнуть сразу на «страницу 37», но это редко бывает реальным требованием. Дополнительный столбец `id` сохраняет стабильный порядок, когда метки времени совпадают.

### 6. Партиционировать большие таблицы

Декларативное **партиционирование таблиц** делит одну логическую таблицу на дочерние на том же сервере, обычно по времени:

```sql
CREATE TABLE events (
  id         bigint      NOT NULL,
  created_at timestamptz NOT NULL,
  payload    jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
```

Запросы с фильтром по `created_at` затрагивают только подходящие партиции (**отсечение партиций**, partition pruning). Вместо огромного `DELETE` удаление старых данных превращается в мгновенный `DROP TABLE events_2025_10`, который не оставляет работы для `VACUUM`. Документация PostgreSQL отмечает, что партиционирование окупается в основном тогда, когда таблица больше оперативной памяти сервера. Несколько тысяч партиций планировщик выдерживает, только если запросы отсекают большинство из них; иначе растут время планирования и расход памяти. Первичные и уникальные ключи должны включать ключ партиционирования.

### 7. Пул соединений

PostgreSQL запускает по одному процессу ОС на соединение. Тысячи в основном простаивающих соединений от автомасштабируемых серверов приложений тратят память и снижают пропускную способность. Пул вроде **PgBouncer** (или управляемый: RDS Proxy, Supavisor или встроенные в хостинговые Postgres) мультиплексирует множество клиентских соединений на несколько десятков серверных:

| Режим PgBouncer | Серверное соединение удерживается на | Оговорки |
|---|---|---|
| Сессия | Всю сессию клиента | Безопасно для всего, но экономит мало |
| Транзакция | Одну транзакцию | Обычный выбор. Ломает состояние сессии: `SET`, `LISTEN`, сессионные advisory-блокировки, курсоры `WITH HOLD`. Подготовленные выражения на уровне протокола работают с PgBouncer 1.21 через `max_prepared_statements`, а с 1.24 включены по умолчанию (200). |
| Оператор | Один оператор | Нет транзакций из нескольких операторов |

Размер серверного пула подбирайте около числа ядер, умноженного на небольшой коэффициент, а не по числу клиентов. Модель MySQL «поток на соединение» выдерживает больше соединений, но пул в приложении или через ProxySQL всё равно полезен.

### 8. Подтянуть схему — разумно

- Используйте правильные типы: целые и `bigint` для ID (32-битный `INT` ограничен значением 2 147 483 647 — это меньше 25 дней при 1000 вставок в секунду), `numeric`/`DECIMAL` для денег, `timestamptz` для моментов времени, `boolean` вместо `'Y'/'N'`.
- Объявляйте `NOT NULL`, где значение обязательно. Это прежде всего инструмент корректности. MySQL отмечает ещё и небольшую выгоду для хранения и индексов.
- Большие бинарные данные держите в [объектном хранилище](/data/object-storage/), а в строке храните ключ.
- В InnoDB держите первичные ключи компактными, потому что каждая запись вторичного индекса содержит первичный ключ.

## Мифы и устаревшие советы

| Совет, который ещё встречается | Статус в 2026 году | Что делать вместо этого |
|---|---|---|
| «Используйте `CHAR` вместо `VARCHAR` ради скорости» | **Неверно для PostgreSQL.** Его документация говорит, что между `char(n)`, `varchar(n)` и `text` нет разницы в производительности, а `char(n)` обычно самый медленный из-за дополнения пробелами. В MySQL InnoDB (строки DYNAMIC, `utf8mb4`) `CHAR(n)` на деле не имеет фиксированной ширины: хвостовые пробелы обрезаются, резервируется *n* байт, а большие столбцы `CHAR` хранятся как переменной длины. | PostgreSQL: используйте `text` или `varchar(n)`, когда нужен предел. MySQL: `CHAR` — только для действительно фиксированных кодов (коды стран, хеши в однобайтовой кодировке). |
| «`VARCHAR(255)` — эффективный максимум» | **Привычка.** Граница 255 в MySQL измеряется в **байтах**: от неё зависит, будет ли префикс длины 1 или 2 байта. С кодировкой по умолчанию `utf8mb4` (до 4 байт на символ) её превышает уже `VARCHAR(64)`. В PostgreSQL такой границы нет. | Выбирайте пределы из предметной области (email укладывается в 254 символа) или используйте `text` плюс `CHECK`. В MySQL завышенные пределы всё же мешают при индексировании: ключ ограничен 3072 байтами, поэтому `VARCHAR(1000)` в `utf8mb4` (до 4000 байт) нельзя проиндексировать целиком. |
| «Включите / настройте кэш запросов MySQL» | **Его больше нет.** Объявлен устаревшим в 5.7.20 и **удалён в MySQL 8.0**, потому что становился узким местом при параллельной нагрузке на многоядерных серверах. | Кэшируйте в приложении или в Redis/Valkey с явной инвалидацией; см. [стратегии кэширования](/caching/cache-strategies/). |
| «Отключите индексы, загрузите, включите обратно» | Отчасти верно. `ALTER TABLE ... DISABLE KEYS` документирован только для таблиц MyISAM. | Загружайте в таблицу без вторичных индексов и создавайте их потом, используйте `COPY` или `LOAD DATA`, вставляйте пачками. |
| «Используйте `TEXT` для булева полнотекстового поиска» | Совет эпохи MyISAM | Используйте полнотекстовый индекс движка (`tsvector` и GIN в PostgreSQL, `FULLTEXT` в InnoDB) или поисковый движок. |
| «Нагружайте через `ab`» | Измеряет HTTP, а не базу, и только один URL | Используйте `pgbench` или `sysbench` для базы и k6 или Locust для сквозной нагрузки. |

## Компромиссы

| Техника | Выигрыш | Цена |
|---|---|---|
| Денормализованные столбцы и счётчики | Дешёвые горячие чтения без соединений | Усиление записи, расхождения, конкуренция за блокировки на горячих строках |
| Материализованные представления | Заранее вычисленные агрегаты без кода в приложении | Устаревание между обновлениями; полный пересчёт в PostgreSQL |
| Больше индексов | Быстрее селективные чтения, сканирование только по индексу | Медленнее запись, больше памяти и диска, больше работы `VACUUM` |
| Партиционирование таблиц | Отсечение партиций, мгновенное удаление старых данных, меньшие индексы на партицию | Накладные расходы на планирование; ограничения ключей должны включать ключ партиционирования |
| Пул соединений (режим транзакций) | Много клиентов на немногих серверных соединениях | Ломаются сессионные возможности; ещё один компонент |

<Aside type="note" title="На собеседовании">
- На вопрос «база тормозит» начинайте с измерений: какой запрос, как часто, какой план. Не прыгайте сразу к шардированию или NoSQL.
- Спроектируйте индекс под заданный запрос вслух: сначала столбцы с равенством, затем диапазон или сортировка, подумайте о покрытии. Упомяните цену для записи.
- Знайте N+1 и пагинацию по ключу — оба вопроса всплывают при проектировании API.
- Если денормализуете, скажите, кто поддерживает копии согласованными и что будет, если они разойдутся.
- Плюсом будет знание того, что кэш запросов MySQL удалён в 8.0, а `CHAR` в PostgreSQL не быстрее.
</Aside>
